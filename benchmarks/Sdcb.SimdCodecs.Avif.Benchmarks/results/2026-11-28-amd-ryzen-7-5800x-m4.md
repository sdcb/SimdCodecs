# AVIF decode benchmark, 2026-11-28, M4 (76f0a70)

Machine: AMD Ryzen 7 5800X 8-Core Processor, Windows 11 Pro 10.0.26200 x64, .NET 10.0.15, 16 logical CPUs, Vector128 / Vector256 true, Vector512 false.

Competitors, in-process on the same byte array: libavif 1.4.2 with dav1d 1.5.5 (P/Invoke, vcpkg build), and Magick.NET (multi-core table only). All numbers are medians in milliseconds; "ours RGBA" goes through the public decode API to 8-bit RGBA, like libavif's RGB conversion.

Commands, from the repository root (`dotnet run --project benchmarks/Sdcb.SimdCodecs.Avif.Benchmarks -c Release -- …`):

```
verify; equivalence; single --reps 5; multi --reps 7 --magick; anim --reps 5
AVIF_STAGE_TIMERS=1 stages --reps 3;  AVIF_STAGE_TIMERS=1 stages --multi --reps 5;  AVIF_STAGE_TIMERS=1 stages --anim --reps 3
ablate --reps 3; ablate --anim --reps 3
baseline <ref> + ab [--multi] [--anim]   (the A/B history below)
```

Magick.NET writes a temporary file per decode; on this machine `%TEMP%` is closed to it, so the run set `TMP`, `TEMP` and `MAGICK_TEMPORARY_PATH` to a writable folder.

## Summary

- **Multi-core (16 threads):** ahead of libavif[dav1d] on grid images (0.39x; our grid cells decode in parallel, and dav1d gains little from its threads on them: 559 ms at 16T vs 543 ms at 1T), level on the 10-bit alpha photo (1.06x), behind on single-item images: 1.4x to 2.6x. Magick.NET takes 3x to 10x our time on every image.
- **Single core:** 2.4x to 4.0x dav1d's time. dav1d's hand-written assembly does per core what our Vector128 / Vector256 kernels and scalar code do. About half of our single-core time is entropy decoding (the `parse` column), which is bound by its dependency chain (~5 ns per symbol, measured in M4; local micro-optimisations stayed within noise).
- **Animations:** 1.4x (10-bit photo) to 4.4x (4:4:4 screen content) dav1d's time on one core. Frames of an animation decode one after another (each depends on the previous), so threads only help inside a frame.
- **Correctness first:** `verify` passes on every image (YUV planes are bit-exact against dav1d in the test suite; RGBA differs only in the RGB conversion, which is ours by design), and `equivalence` finds the serial and parallel decodes bit-identical.

### Stage timers, 16 threads

`total`, `tiles`, `recon` and `post` are wall time; `modeinfo` / `mistore` / `coeffs` are CPU time summed over threads, so `tile-rest` (wall minus CPU sums) goes negative wherever tiles decode in parallel and is not meaningful there. Grid images time each cell's tiles separately, so their `tiles` and `post` are sums over concurrently decoded cells.

## A/B history of this round (same process, baseline vs working tree)

Every row's output was byte-identical to its baseline (all frames, for animations) before timing. B/A below 1 is faster.

## Next targets

- Single-core kernels: deblocking is still scalar per sample (12 to 19% of single-core time on photos); inter prediction and intra prediction are the largest reconstruction shares on screen content and animations.
- Identity-matrix (GBR) and premultiplied colour conversion still use the per-pixel path.
- Entropy decoding (40 to 66% of single-core time) is the floor; only parallelism across tiles and frames can hide it, and a one-tile frame cannot be split.
