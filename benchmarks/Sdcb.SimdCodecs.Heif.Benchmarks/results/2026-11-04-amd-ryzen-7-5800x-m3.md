# HEIF decode — 2026-11-04 — AMD Ryzen 7 5800X (M3, performance)

**Purpose:** record where M3 left the HEIF decoder against the M1/M2 baseline
([`2026-11-03-amd-ryzen-7-5800x-m1-baseline.md`](2026-11-03-amd-ryzen-7-5800x-m1-baseline.md)) and its competitors,
and how each stage earned its share. Every number below was measured in the same session, on the same machine,
with the harness of this project (`verify` all-green before each run).

## Machine

- CPU: AMD Ryzen 7 5800X (8 cores / 16 logical)
- OS: Windows 11 Pro for Workstations 10.0.26200
- .NET: SDK 10.0.400, runtime 10.0.11 (win-x64)
- Vector128 / Vector256 hardware-accelerated, Vector512 not
- Competitors (same process, same `byte[]`): libde265 1.1.1, libheif 1.23.1 (vcpkg), Magick.NET-Q16-HDRI 14.13.1

## Targets (from the M3 brief) and where they ended

| target | M1/M2 baseline | M3 | |
|---|---|---|---|
| single core, HEVC stage ≤ libde265 | 1.52–1.85× slower | **0.68–0.87×** (BDN), 0.73–0.89× (`single`) | met |
| multi-core grids stay ahead of libheif | 0.55–0.71× | **0.24–0.25×** (BDN) | met |
| multi-core single items ≤ 1.0× libheif | 1.36–1.75× | **0.28–0.32×** (BDN) | met |
| single core end to end ≥ 2× faster than Magick.NET | 1.1–1.85× | **2.1–3.8×** (`single`) | met |
| peak rise, 12.6 MP grid ≤ 64 MB | 132 MB | **75 MB** (libheif 80) | not met, see below |
| peak rise, 50 MP grid ≤ 256 MB | 516 MB | **230 MB** (libheif 373) | met |

The 12.6 MP grid misses its memory target by 11 MB. The measurement is the first decode in a fresh process, so it
includes JIT-compiled code and sixteen thread-pool threads each holding one tile's working set (pooled planes,
side information, SAO strip, about 1 MB); with one small decode before the baseline the same grid rose 68 MB
before the SAO strip change. What remains is the cost of decoding sixteen tiles at once; it is below libheif's
rise on every grid fixture.

## Where the time went, stage by stage

Each stage was measured as an interleaved A/B against the commit before it (`quick`: our decoder alone, pinned
to CPU 2, median of 3 rounds × 5 runs); the numbers are in each commit message. Attribution came from ablation
(`ablate`: one stage switched off at a time, single core), never from a profiler or a subtraction.

| commit | stage | why it got faster | 12.6 MP Main stage, before → after |
|---|---|---|---:|
| 4471422 | inverse transform | naive O(N³) triple loop → int32 matrix products over the coded rectangle only, even/odd symmetry, 8 / 4 lanes; scaling fused into parsing, residual add fused into the kernel | 632 → 463 |
| 89135ed | CABAC | bit-at-a-time reads → 64-bit look-ahead window, one-step LPS renormalisation, packed transition tables | 468 → 441 |
| 3effb03 | SAO | per-sample neighbour / slice / bypass checks → CTB-level proof and int16 row kernels | 455 → 397 |
| 3c58906 | colour | per-pixel scalar with three clamps → int32 row kernels (RGBA end to end 459 → 433) | — |
| ca6c626 | intra prediction | z-scan availability per 4 samples → O(1) reconstructed-map lookup; vector planar / angular | 397 → 342 |
| fb0ed37 | memory | tiles written straight into the output in any layout, pooled planes, SAO strip instead of a plane copy | 349 → 356 (neutral) |
| 6f9172d | parallelism | WPP wavefront and parallel filter / colour passes for a lone image (fuji multi-core 28 → 11 ms) | — |

Ablation at the end (single core, ms, 12.6 MP Main grid): full 388; residual path 80, intra 123, deblocking 69,
SAO 53, colour 53, everything else (CABAC, residual syntax, quadtree, side information) 198. Parsing is now the
largest share; it is one serial dependency chain per CTB row.

## Correctness and robustness at the end

- `verify`: HEVC stage vs libde265 and grid composition vs libde265 tiles 0-diff on all fixtures; `equivalence`
  (serial vs parallel tiles) 0 bytes; both goldens unchanged.
- `HeifEquivalenceTests` (inverse transform, SAO edge / band, colour, intra: every tier vs the definition or the
  scalar twin on random inputs), `HeifTransformTests` (random clap / irot / imir chains, every layout and stride),
  `HeifWavefrontTests` (parallel = serial planes, wavefront actually taken) — pass on Vector256, Vector128 and
  scalar; CI runs the HEIF tests on x64 Vector128, x64 scalar and arm64.
- Fuzz soak (`HeifFuzzTests`) after the last change: 300 000 iterations on the default tier in 8 processes, plus
  30 000 each with `DOTNET_EnableAVX2=0` and `DOTNET_EnableHWIntrinsic=0`; every shard `Failed: 0`.
- NativeAOT and Mono AOT (browser-wasm) smoke tests: output identical to the JIT.

## Reproducing

```bash
export TMP=$PWD/artifacts/tmp TEMP=$PWD/artifacts/tmp   # BenchmarkDotNet's child build fails on this machine otherwise
HEIF_NATIVE_DIR=C:/_/3rd/vcpkg/installed/x64-windows/bin \
  dotnet run -c Release --project benchmarks/Sdcb.SimdCodecs.Heif.Benchmarks -- verify   # then single / multi / peakmem / ablate / quick
HEIF_NATIVE_DIR=... dotnet run -c Release --project benchmarks/Sdcb.SimdCodecs.Heif.Benchmarks \
  -- --filter "*HeifDecodeBenchmarks*" --warmupCount 3 --iterationCount 10
```

BenchmarkDotNet locates its project by name under the repository root: a `git worktree` of the repository inside
it (for an A/B baseline) makes the project name ambiguous and every case fails with `NA`; keep such worktrees
outside the repository.
