# HEIF decode baseline — 2026-11-03 — AMD Ryzen 7 5800X

Whole-image decode of the six M1 fixtures. **Measurement only — M1 was written for correctness, not speed; no optimisation was done for this baseline.** It exists so M2 has a starting point to beat, recorded the same way every later result is recorded.

Contestants: **Sdcb.SimdCodecs.Heif** `HeifDecoder.Decode` (container + HEVC intra + colour → RGBA8, grid tiles decoded on the thread pool) and `DecodeYuv` (the same decode, stopped at the three planes); **Magick.NET 14.13.1** (ImageMagick → libheif → libde265 → Q16 HDRI, then `GetPixels().ToByteArray(RGBA)`); **ffmpeg 8.1.2** HEVC decode to raw YUV, for reference on the HEVC stage alone.

## Machine

- CPU: AMD Ryzen 7 5800X (8 cores / 16 logical)
- OS: Microsoft Windows 10.0.26200 (X64)
- .NET: 10.0.11 (win-x64), process X64
- Vector128.IsHardwareAccelerated: True, Vector256.IsHardwareAccelerated: True, Vector512.IsHardwareAccelerated: False
- GC: workstation; no server GC; tiered compilation default
- **Not BenchmarkDotNet.** Times are the median of 5 runs after one warm-up, in one process, ours and Magick interleaved per file. The single-core rows pin the whole process to one logical CPU (`ProcessorAffinity = 1`). Treat 5–10 % as run-to-run noise; a real M2 A/B must use BenchmarkDotNet in the benchmark project, as the other codecs do.

## What this says

- **Against libheif (via Magick), multi-core, we are already 3.4–3.9× faster** on the tiled phone images, because the grid tiles decode in parallel and libheif's own threading does not help the way it helps a video sequence. On single-item images there is nothing to parallelise and the win is only 1.2–1.5×.
- **Single core, against libde265, we are faster on every fixture** (1.2–1.5× on the phone images, 1.5× on testsrc2) — the "not embarrassing" reading is right, but it is a race against a decoder tuned for video, not against a SIMD-optimised image codec.
- **Single core, against ffmpeg's HEVC decoder, we are 2–5× slower per core** (19–21 MP/s vs 45–101 MP/s of CPU time). That is the real gap: our CABAC, residual parsing and reconstruction are scalar, with no AVX2 anywhere.
- **Memory is the clearest weakness.** Managed allocation is 2.7× Magick's on the phone images (128–132 MB vs 48 MB for a 48 MB output) and 2.7× at 50 MP; peak working set is 2.3–2.7× the output for `DecodeYuv`-style composition because every tile's three 16-bit planes are held until the canvas is assembled. Neither figure is acceptable for a codec shoot-out.
- **The colour pass is 25–32 %** of the multi-core decode and is pure scalar per-pixel arithmetic — the cheapest large win available.

## Reproducing

The scratch harness lives in the git-ignored `artifacts/` tree (not in this repo's benchmark project, and not suitable as a baseline for M2 comparisons): one process, median of 5, `single` / `breakdown` / `mem` modes. Fixtures are fetched with `bash tests/Sdcb.SimdCodecs.Tests/Oracle/heif/fetch.sh`; ffmpeg must be the pinned 8.1.2. M2 should replace this with BenchmarkDotNet cases in `benchmarks/Sdcb.SimdCodecs.Heif.Benchmarks` and re-record a baseline before changing anything.
