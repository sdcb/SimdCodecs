# M5 — closing the gap to libjpeg-turbo (2026-10-24, AMD Ryzen 7 5800X)

## Summary

M5 changed **no output byte**. The golden, every ISA tier and the accuracy tables are unchanged:
`ab` reports "current/baseline identical" against the M4 end state on every file.

Quick A/B subset (13 files, same process, BenchmarkDotNet medians), final state `12ebd76`:

- **0.82× libjpeg-turbo's decode time** (geomean). Every file is faster than turbo.
  - At the M4 end this subset was 1.35×.
- **0.64× of the M4 end decoder** (`34e9b5f`).
- By kind, ours ÷ turbo:

  | Kind | Ours ÷ turbo |
  |---|---:|
  | Grayscale | 0.60× |
  | Progressive | 0.74× |
  | 4:4:4 | 0.80–0.84× |
  | 4:2:0 / 4:2:2 | 0.85–0.88× |
  | Camera original | 0.89× |
  | Restart intervals | 0.87× |

- The 4:2:0 q75 3 MP files from the question that started M5 (1.42× at the M4 end) now run at
  0.83–0.87× (`12ebd76` vs `ddd5202` A/B).

Machine:
- AMD Ryzen 7 5800X, 16 logical processors.
- Windows 10.0.26200, .NET 10.0.11, RyuJIT x86-64-v3.
- AVX2 and BMI2 present, no AVX-512.
- Workstation non-concurrent GC.

The full-matrix run (all 446 files, `bench` + `peakmem` + `accuracy`) has not been done in this

How to read the columns:
- **Stage columns** (IDCT, upsample, colour) are current minus current-with-that-stage-skipped.
  Ablations interact, so a small negative value is noise.
- **entropy** is decoding with every block dropped on arrival and no rows emitted.
- **rest** is (entropy + rest) − entropy.
- **turbo planes** is libjpeg-turbo decoding only to component planes (entropy + IDCT, as a
  black box).
- Against that column, our entropy + IDCT is now below turbo's on every file. The remaining
  per-stage difference is upsample + colour; turbo's "up+colour" excludes the cost of writing
  its planes.

## Measured and not kept

- **AAN-style 5-multiply float IDCT** (hand-derived from the T.81 definition, checked against it
  to 1e-12 in double). Not faster: 1.01–1.04×.
  - Zen 3 issues float adds and multiplies on separate pipes, so cutting multiplies from 22 to 5
    does nothing while the adds (29 vs 28) and the transposes stay.
  - It would have moved the golden.
- **Hybrid FMA IDCT** (AAN even half, direct odd half with fused multiply-add). Only 1–2% after
  the native-min/max fix (0.96–1.01×).
  - It would move the golden.
  - It falls back to software FMA on pre-FMA x64.
  - Parked.
- **Decode a whole MCU, then transform its blocks** (tried twice): 1.02–1.07× slower.
  - Decoding a block and transforming it straight away lets the out-of-order core overlap one
    block's serial Huffman chain with the previous block's IDCT.
- **12-bit Huffman lookup**: 1.01× overall, 1.07× on 444-q90 (L1 pressure). Kept 11 bits.
- **16-bit fixed-point YCbCr** (analysis only). A single `pmulhrsw` per term cannot reproduce the
  T.871 value exactly, giving about 0.7% of channels off by one.
  - Estimated cost: ~0.07 dB on 4:2:0.
  - 4:4:4 has only +0.02–0.04 dB of PSNR over turbo to spend.
  - Not done.

## Where the time goes now (420-q50/q75, 3 MP)

| Stage | Share |
|---|---:|
| Entropy decoding | ~45% |
| IDCT | ~25–30% |
| Colour (including the 12 MB RGBA store) | ~18% |
| Upsample | ~6% |

The Huffman decoder runs at about 8 cycles per symbol. That is the latency of its dependency
chain: table load → shift → next index.
