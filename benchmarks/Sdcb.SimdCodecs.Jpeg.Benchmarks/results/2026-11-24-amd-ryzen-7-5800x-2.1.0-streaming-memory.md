# JPEG streaming memory experiment

- Date: 2026-11-24
- CPU: AMD Ryzen 7 5800X
- OS: Windows 11 10.0.26200
- Runtime: .NET 10.0.15, SDK 10.0.404
- SIMD: AVX2 enabled, AVX-512 unavailable
- Build: Release, current 2.1.0 sources

This is an end-to-end smoke measurement on the prepared 12 MP `420-q90-12mp/landscape-almsee` JPEG from the CC0 corpus. Each case ran in a fresh child process, three times, and the median was selected by peak working-set rise. Working set was sampled during the operation. The decoder output hash is SHA-256 over all output bytes. The encoder source experiment uses a deterministic RGB image at the same 4000×3000 dimensions so the source can either be a complete array or a 16-row producer.

| operation | input retained by caller | output staging | baseline WS | peak WS | peak − baseline | output bytes | output SHA-256 |
|---|---:|---:|---:|---:|---:|---:|---|
| buffered decode | 2,700,891 B JPEG | 48,000,000 B RGBA | 75.1 MiB | 76.9 MiB | 1.8 MiB | 48,000,000 | `4ECBA113EB590B31087C1C0F5C31F526468A08383266DA39F2B38D459D257DF5` |
| streamed decode | file stream | 256,000 B, 16 RGBA rows | 27.8 MiB | 30.0 MiB | 2.2 MiB | 256,000 | `4ECBA113EB590B31087C1C0F5C31F526468A08383266DA39D257DF5` |
| buffered encode | 36,000,000 B RGB source | returned JPEG byte[] | 63.6 MiB | 71.9 MiB | 8.2 MiB | 2,343,645 | `6FE3544AB89C25B349AA26586774742B2845798C53F68B4E09464797875F085D` |
| streamed encode | 192,000 B, 16 RGB rows | `ArrayBufferWriter` JPEG | 29.5 MiB | 38.0 MiB | 8.5 MiB | 2,343,645 | `6FE3544AB89C25B349AA26586774742B2845798C53F68B4E09464797875F085D` |

The decode result is byte-for-byte identical. Its absolute peak working set fell from 76.9 MiB to 30.0 MiB, a 46.9 MiB reduction. The caller-owned output storage fell by 45.6 MiB because the streamed reader writes a reusable band.

The encode result is byte-for-byte identical. With a row-producing caller, absolute peak working set fell from 71.9 MiB to 38.0 MiB, a 33.9 MiB reduction. The encoder itself has similar transient work in both paths when a caller already retains the complete 36 MB RGB array. The memory benefit comes from allowing the caller to release that array and provide rows as they arrive.

The sample is a baseline sequential JPEG. Progressive JPEG and options that require buffered fallback are outside this experiment and report `IsStreaming == false` by design.

## High-level full-pixel decode

The same JPEG was also measured through the public high-level stream API. The input was wrapped as a non-seekable stream and opened with `forwardOnly: true`; the operation was `decoder.GetFrame(0).Decode()`, which returns a complete `IDecodedImage`.

| operation | input retained by caller | output pixels | baseline WS | peak WS | peak − baseline | pixel bytes | pixel SHA-256 |
|---|---:|---:|---:|---:|---:|---:|---|
| `ImageCodecs.Decode(File.ReadAllBytes(...))` | 2,700,891 B JPEG | complete `IDecodedImage` | 25.7 MiB | 67.8 MiB | 42.1 MiB | 36,000,000 | `74493E2B07B572F0EF2E4F315E26460EA783CC3213CE024E4D96AFA8B5677C4C` |
| `ImageDecoder.Open(nonSeekable, forwardOnly: true).GetFrame(0).Decode()` | forward-only stream | complete `IDecodedImage` | 25.1 MiB | 70.6 MiB | 45.6 MiB | 36,000,000 | `74493E2B07B572F0EF2E4F315E26460EA783CC3213CE024E4D96AFA8B5677C4C` |

The high-level API produced identical full-pixel bytes, but this experiment does not show a peak-memory reduction. The complete 36,000,000-byte pixel allocation dominates the 2,700,891-byte compressed input, and process-level sampling noise is larger than the input-buffer saving. The low-level row-reader experiment demonstrates the substantial reduction only when the consumer also accepts row bands instead of retaining a complete pixel object.
