# M0 — defined decoder arithmetic + measurement loop — 2026-10-24 — AMD Ryzen 7 5800X

M0 replaces the stb_image integer sample pipeline with arithmetic defined in-repo from T.81 / T.871,
moves the decoder golden (`jpeg-oracle-golden.tsv`) once, and adds the same-process A/B + ablation
loop that every later milestone is measured with. **No optimisation was done**; the A/B below is the
starting line for M1–M4.

## What changed in the output

| Stage | Before (stb port) | After (M0) |
|---|---|---|
| IDCT | 12-bit fixed-point integer, 2 extra bits between passes | IEEE single precision, separable even/odd split from the A.3.3 definition, no FMA; scalar / Vector128 / Vector256 bit-identical |
| Chroma upsampling | ¾/¼ interpolation rounded to 8 bits (last sample of a horizontal-2× row used the wrong neighbour) | Same interpolation at 16× scale, **never rounded**; edge handled symmetrically |
| YCbCr → RGB | 20-bit fixed point, Cb·G term truncated to 16 bits | T.871 coefficients in single precision on the unrounded chroma, round half up |

Entropy decoding is unchanged (still 0 coefficient mismatches against libjpeg-turbo).

Reading it: M0 is 1.19× slower than the stb baseline, almost entirely in colour conversion, which
is now a per-pixel scalar float loop (~12–13 ms per 3 MP, about half the decode). That kernel is
rewritten in M2 (fused upsample + convert + RGBA pack, Vector256 → Vector128 → scalar, bit-identical
to this definition). Ablation columns are differences of medians and carry noise; when a skipped
stage changes the data a later stage sees (zero planes after `NoIdct`), the difference can even go
negative (camera file).
